# UE 技术学习路线与阶段验收

这份路线把真实 UE 实验逐步接入业务和引擎运行环境。当前先搭建 CLI 的 Commandlet 实验台；下表中的后续阶段是扩展计划，不表示已经实现。实际可运行内容与验证状态见 [README](../README.md) 和 [MEMORY](memory/MEMORY.md)。

## 路线总览

| 阶段 | 核心问题 | 首批实验 / 产物 | 完成边界 |
| --- | --- | --- | --- |
| 0 环境 | 能否稳定构建并运行真实 UE 代码？ | 工具链诊断、UE 版本探针、失败退出码、日志 | 能从 CLI 重跑一个真实 API 探针；说明依赖和耗时 |
| 1 Core 数据流 | 信息怎样创建、存储、转交和反馈？ | `TArray` 批量输入、稳定快照、普通委托、接收结果 | 正常、空输入和批量情况下结果可检查；知道所有权 |
| 2 UObject | 引用和回调怎样跟随对象生命周期？ | `NewObject`、强/弱引用、受控 GC、弱绑定委托、反射字段 | 强引用与弱引用结果可解释；对象失效后不解引用悬空地址 |
| 3 编码与扫描 | 字段精度和批量大小怎样影响成本？ | 内存序列化、格式版本、量化、压缩、往返、参数扫描 | 有字节/误差/耗时数据和选择依据；损坏输入能拒绝 |
| 4 World 与时序 | 注册、初始化、BeginPlay、Tick、Timer 怎样组合？ | 最小 World runner、组件注册、Tick 前置依赖、延迟反馈 | 能解释消费者读到哪一帧；退出时完成资源清理 |
| 5 引擎数据交接 | 游戏状态怎样交给其他线程或渲染侧？ | 不可变快照、任务完成、游戏线程应用、CPU 渲染命令与 fence | 有线程/帧/生命周期证据；明确 CPU 与 GPU 完成的区别 |
| 6 真实联网 | 状态怎样跨进程传递并收敛？ | 真实服务端 + 两客户端、RPC/属性复制、Fast Array 对照、网络 trace | 初始/增量/迟加入/丢包/重连均通过，测到实际网络流量 |
| 7 项目专题 | 如何选择适合 MMORPG 或 SLG 的方案？ | 批量属性、背包增量、战斗参数或资源结算专题 | 给出业务预算、参数和测试证据，能接入最小项目 |
| 8 真实呈现与发布 | 数据信息最终怎样形成正确反馈？ | 最小真实 RHI 客户端、GPU/画面检查、目标配置和机器复测 | CPU 数据、GPU/画面和实际部署表现都验证 |

阶段可围绕一个专题交错推进。无需把所有 Core API 学完才接触 World 或网络；先解决当前情境最需要的依赖。

## 第一阶段的学习顺序

1. 运行环境探针，确认用的是 UE 类型和库，并记录具体引擎版本、编译器、SDK 与 runner。
2. 用 `TArray` 做“生成批量属性 → 交给消费者 → 返回统计”，观察容量、有效范围、复制和移动；区别 `Reserve` 与元素数量。
3. 加入 UObject 接收者和弱委托，比较接收者存活、强引用保留及回收后的行为。先预测，再受控触发 GC。
4. 对一组明确的数据字段执行编码与还原，比较原始字段、量化字段和压缩结果。输入规模与分布改变时重新比较。
5. 完成独立答题：先基础，再边界，再组合情境。参考答案用于解释差异和排查环境。

这组实验提供进入 UE 的真实 API 基础和数据处理经验。它尚不包含真实网络复制、业务加密协议、自动 World Tick、真实渲染线程或 GPU 验证。

## MMORPG 专题：单位属性与背包增量

先写清楚预算：可见单位数量、属性更新比例、玩家连接数、每连接带宽、可接受延迟、数值误差与敏感字段。下面的数值仅作扫描起点，不能直接作为项目推荐参数。

| 逐步实验 | 可变化输入 | 检查 / 反馈 | 后续整合 |
| --- | --- | --- | --- |
| 属性批量编码 | 32 / 256 / 1,024 条；稀疏/密集变化 | 往返一致、总字节、每条成本、处理耗时 | `NetSerialize` 或既定复制方案 |
| 位置和属性量化 | 业务范围、步长、边界值 | 最大误差、越界策略、解码范围 | 真实复制中的位数与网络包 |
| 压缩阈值 | 小批次、大批次、重复数据、随机数据 | 压缩收益、编码/解码时间、无收益回退 | 实际包处理链，避免重复压缩 |
| 背包/Buff 增量 | 新增、修改、删除、全量加入 | 状态一致、脏标记、客户端通知、版本 | 真实 Fast Array 与连接场景 |
| 连接与安全 | 身份错误、损坏包、旧序号、重放、重连 | 拒绝原因、无重复应用、密钥和会话规则 | 经评估的认证与加密传输 |

本地扫描只是筛选候选参数。进入真实网络后，要把连接开销、包头、复制元数据、重传或丢弃行为、发送频率和多客户端成本加回来。对于被接收者不需要的数据，先考虑可见性和相关性，减少需要编码与发送的工作。

真实网络验收至少包含：服务端与两个客户端一致；后加入客户端得到正确全量；稀疏变化只影响需要的状态；丢包和延迟下最终收敛；断开重连后不会重复执行旧业务操作；带宽和收敛时间在预算内。使用网络 trace 获取实际包证据。[Epic：Networking Insights](https://dev.epicgames.com/documentation/unreal-engine/networking-insights-in-unreal-engine?lang=en-US)

认证、加密、完整性和重放处理需要端到端连接场景。序列化和压缩通过不能作为这些要求的验收。

## SLG 专题：资源、时间与数值命令

先确定权威状态的位置，并定义每个字段的单位、范围和精度。UE 的客户端/服务端模型通常由服务端维护权威状态；玩法规则仍需显式设计。[Epic：Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine?lang=en-US)

| 逐步实验 | 重点 | 验收 |
| --- | --- | --- |
| 资源加减与批量结算 | 最小单位整数、乘除顺序、中间值宽度 | 边界处没有溢出或静默截断；规则明确 |
| 百分比与成长 | 定点倍率、舍入、累积误差 | 参考计算对拍；长期累计符合预算 |
| 命令应用 | 请求 ID、权限、序号、预期版本、拒绝原因 | 重复命令不重复扣费；过期命令不覆盖新状态 |
| 状态应用 | 版本、快照、增量、乱序 | 初始状态正确；旧增量不会回退状态 |
| 时间与离线收益 | 服务端时间基准、时间段上限、结算顺序 | 时钟跳变与重复上线不会重复发放 |
| 真实联网 | 请求 → 服务端校验结算 → 更新 → 客户端反馈 | 两客户端所见一致，拒绝和重试反馈可解释 |

定点数是明确精度和舍入的工具。还要固定结算顺序、检查中间结果范围，并验证使用到的算法，才能讨论重放或跨机器一致性。若涉及持久化和跨服务事务，它们属于后续后端整合；本地 UE 数值实验不能代替数据库事务与恢复验证。

## 不看画面时仍要保留的渲染知识

可以先学习数据侧：游戏线程持有 UObject 状态，消费者通过快照读取；组件注册与状态更新可能安排后续工作；CPU 命令排队、CPU fence、GPU fence/readback 是不同的完成条件。跨线程代码必须有明确的数据归属和生命周期。[Epic：Threaded Rendering，UE 5.6](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine?application_version=5.6)

在 NullRHI 下完成这些题，只能覆盖实际执行的 CPU 路径。真实 RHI 场景仍需要验证材质参数或实例数据是否到达 GPU、何时反映到画面、资源释放是否安全、更新频率的真实成本。无显示阶段可以把这些列为待完成项，不需要现在创建大型场景。

## 每阶段交付什么

每个阶段至少留下一个可运行实验、一份独立答题骨架、一套有效验收、一份独立参考答案，以及一次结果记录。每个项目专题额外留下“输入范围 → 参数选择 → 字节/误差/耗时 → 未覆盖环境”的表。

适合迁入真实项目的标准是：能说清 API 的前置条件、调用顺序、数据所有权、失败与恢复；参数由约束和测量支持；涉及跨线程、网络或 GPU 的结论有对应环境的证据。课程阶段通过是迁移起点，项目目标规模和部署环境仍需自己的验收。
