# 用实验学习真实 UE 的流程

这里的目标是能够在真实项目中选择和组合 UE API，解释数据何时产生、交给谁、由谁消费、怎样反馈。API 能编译只是第一步。每个主题都应沿着“探针 → 调用关系与边界 → 参数扫描 → 项目情境 → 引擎整合”推进。

基础环境使用本机 UE 5.6.1 的预编译引擎，共用一个 Editor Commandlet，通过命令行运行。日常优先编辑一个实验 `.cpp`；自定义反射类型再增加 `.h`，让 UHT 参与构建。命令和已提供的实验以 [README](../README.md) 为准。

## 先知道实验所在的运行环境

Commandlet 的默认环境没有游戏关卡、Actor 或正常的游戏循环。它适合 Core、UObject、内存序列化等实验，但不会因为链接了 Engine 就自动获得正常的 `BeginPlay`、World Tick、网络复制和渲染流程。[Epic：UCommandlet，UE 5.6](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UCommandlet?application_version=5.6)

因此扩展实验时分开选择承载方式：

| 要验证的问题 | 需要的环境 | 结果能说明什么 |
| --- | --- | --- |
| 容器、名称、普通委托、序列化和压缩 | 当前 Commandlet | 该 UE 版本中这些 API 的本地行为 |
| UObject 引用、弱引用、反射 | Commandlet + 明确的引用和 GC 控制 | 该对象图中的存活、失效与回调行为 |
| Actor、组件注册、Timer、Tick 顺序 | 后续显式建立并推进的 `UWorld` 或最小 Game runner | 所建立 World 的生命周期和帧顺序 |
| 游戏线程到渲染线程的信息交接 | 后续具有真实渲染线程的 runner | 数据副本、线程归属和 CPU 命令完成情况 |
| 实际复制、RPC、连接、丢包与重连 | 后续真实 NetDriver + 多个游戏进程 | 被测网络条件下的端到端状态与流量 |
| GPU 数据、材质、视觉反馈、GPU 时间 | 开启真实 RHI 的最小客户端 | 真实 GPU 执行、读回和画面结果 |

`-NullRHI` 使用空渲染后端，适合无显示运行。[Epic：命令行参数](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-command-line-arguments-reference) 它不能证明 GPU 已执行、GPU 资源内容正确、视觉效果正确或真实渲染性能。某个 CPU 路径在此模式下被跳过时，应在结果中写“未覆盖”；不要把未运行视为通过。

## 每个主题的五步

### 1. API 探针：写出最小可证伪的问题

一次只回答一个问题。例如：“`TArray` 增加元素后，容量何时增长？”“释放最后一个强引用后，这个弱引用是否失效？”“这个压缩格式在当前运行环境能否使用？”

先写预测，再运行。输出至少包括输入、关键状态和返回值；给行为写检查，让错误产生非零退出码。对 `TArray` 可以观察 `Num/Max`、分配字节、构造/析构次数；对生命周期可以观察强引用释放、弱引用状态和回调次数。

完成条件：能解释每个检查为什么成立，并能修改输入让其中一项按预期失败。背下输出不算完成。

### 2. 调用关系与边界：画出先后和归属

把 API 放回完整链路：

```text
生成业务数据
  → 校验合法性
  → 形成稳定的输入或快照
  → 编码 / 入队 / 注册
  → 消费者读取并更新状态
  → 完成通知 / 回调 / 确认 / 错误
  → 释放或复用资源
```

对每个箭头回答五件事：谁拥有数据、谁可以修改、在哪个线程、何时允许下一步、失败后怎样恢复。先后约束必须由明确的依赖或完成条件保证，不能靠“这次打印刚好先出现”。

边界输入至少包含空输入、单元素、最大允许值、重复输入、过期对象、截断数据。可以安全构造的失败路径要执行；会触发未定义行为或引擎致命检查的路径应先做输入拦截或隔离进程，不在主实验中直接制造悬空指针解引用。

Tick 主题要区分 Tick Group 与具体前置依赖。设置间隔、注册状态和所处组都会改变消费者看到的数据帧。API 细节以本机 5.6 头文件及实验为准。[Epic：Actor Ticking](https://dev.epicgames.com/documentation/unreal-engine/actor-ticking-in-unreal-engine)

### 3. 参数扫描：同时衡量正确性与成本

先确定业务约束，再搜索参数。不要仅凭一次耗时或“压缩比最小”选择配置。

| 实验 | 可扫描参数 | 必须同时记录的指标 |
| --- | --- | --- |
| 容器批量更新 | 批量大小、预留量、更新比例 | 分配量、构造次数、处理耗时、结果一致性 |
| 属性编码 | 数值范围、精度、量化位数、字段集合 | 编码字节、最大/平均误差、越界策略 |
| 批量序列化与压缩 | 记录数、变化比例、数据分布、压缩阈值 | 原始/编码/压缩字节、编解码耗时、往返一致性 |
| 后续真实网络 | 更新频率、相关范围、增量比例、连接数 | 实际包字节、收敛延迟、队列积压、丢包下的状态 |
| SLG 数值处理 | 定点倍率、整数宽度、批次和结算顺序 | 精度、上溢边界、结果一致性、处理耗时 |

固定随机种子和数据集；同时测试稀疏变化、密集变化、可重复数据与难压缩数据。性能测量应先预热，再重复测量，记录中位数与较差样本；计时区间外打印日志。把 UE 启动、编译耗时与算法耗时分开。Editor/Development 的结果用于比较本实验中的方案，发布配置和目标机器还需复测。

`FCompression::CompressMemory` 返回成功也可能产生更大的数据，因此要比较实际字节数并考虑保留未压缩版本。是否值得压缩还取决于编码与解码成本。[Epic：FCompression::CompressMemory](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FCompression/CompressMemory)

每次扫描输出应能回答：“在哪组输入和约束下，选择哪个参数？为什么？超过什么范围要重新测试？”

### 4. 项目情境：把多个 API 连起来

每个情境从一条可检查的业务链路开始，不从完整游戏开始。

MMORPG 的第一条链路可以是：“生成 1,000 个单位属性 → 选取变化字段 → 批量编码 → 按收益选择压缩 → 解码 → 更新接收方状态 → 统计错误和反馈”。这可以先用真实 UE 的容器、序列化和压缩 API 在本地完成；此时它仍是数据处理实验。

SLG 的第一条链路可以是：“收到资源消耗命令 → 校验序号和权限 → 在权威状态中结算 → 生成状态版本 → 发送变化 → 接收方应用 → 重复命令不重复扣费”。本地先验证数值规则、结算顺序和版本规则，再接入真实网络。

完成条件：说明输入范围、数据格式、调用顺序、错误码和恢复方式；给出一组默认参数及选择证据；在规模增大和数据分布改变时仍能保持业务约束。

### 5. 真实引擎整合：验证那些本地实验无法回答的事

将情境接入真实 World、Actor、组件或 NetDriver，再验证系统边界。首个联网验收至少使用一个服务端和两个客户端，包含初始同步、增量更新、新客户端加入、丢包/延迟、断开重连和最终状态收敛。

实际网络字节包含复制、连接和包处理开销，不能由内存 buffer 长度直接推算。用 Networking Insights 查看实际包、属性和 RPC 的流量。[Epic：Networking Insights](https://dev.epicgames.com/documentation/unreal-engine/networking-insights-in-unreal-engine?lang=en-US)

UE 的默认联网思路由服务端维护权威状态，客户端接收复制并呈现。应先确定每类数据的权威归属与接收对象，再考虑复制频率与带宽。[Epic：Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine?lang=en-US)

## 两条业务方向的特殊要求

### MMORPG：批量、压缩与保密分别验收

本地序列化回答“能否编码和还原”；压缩回答“是否节省字节、成本多大”；复制系统回答“哪些状态传给谁、何时收敛”。这些结果不会自动组成一个可用协议。

保密要通过后续端到端连接单独验证：认证、会话密钥来源与轮换、完整性校验、连接身份、重放处理、错误包行为及日志中的敏感数据。不要把压缩、Base64、异或、校验和或本地 AES 往返当成网络安全已经完成。应使用经过评估的引擎或传输方案；本仓库第一阶段不设计生产密码协议。

降低传输量先比较“不发送不需要的数据”“只发送变化”“降低不重要状态的频率”，然后比较字段编码与压缩。对背包、Buff 列表等，可在后续真实复制场景比较 Fast Array；新增/修改和删除的脏标记要求不同，单独调用本地序列化函数不能验证客户端通知和复制行为。[Epic：FFastArraySerializer](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/NetCore/FFastArraySerializer?lang=en-US)

### SLG：数值与命令的确定含义

先定义单位、范围、精度、舍入方向和溢出策略。例如资源保存为整数最小单位，百分比保存为约定倍率的整数；乘除时检查中间结果范围。定点数能使规则明确，但不会自动保证所有平台、算法和执行顺序都确定。

分别验证状态同步与命令同步：状态需要版本和覆盖规则；命令需要顺序、幂等与拒绝原因。客户端显示值和服务端结算值可以使用不同表达，但必须明确转换和误差。测试零值、负值是否允许、最大值、连续累积、先乘后除、重复和乱序命令。

## 学习材料与验收的组织

一个课程主题应包含问题说明、独立答题骨架、逐级提示、独立参考答案、验收代码和结果记录。验收分为三级：

1. 基础：正确输入下 API 和业务结果成立。
2. 边界：空输入、上限、重复、失败与失效对象按约定处理。
3. 情境：多阶段调用、参数约束和组合行为成立。

参考答案通过只说明环境和参考实现通过；答题文件必须保持由学习者完成。用参考答案诊断环境时，把结果标成“solution”，不能写成“我已掌握”。

每个主题结束留下简短记录：

```text
问题与预测：
引擎版本 / 构建 / runner / 种子：
输入范围与参数：
实际结果与检查：
API 调用顺序 / 数据归属 / 完成条件：
参数选择及证据：
仍未验证的边界：
迁移到项目时的下一项检查：
```

整个流程以可解释、可重跑、可迁移为完成标准。某个实验的绿色检查只覆盖它声明的环境与断言，不代表网络、渲染或安全的其他阶段已经完成。
